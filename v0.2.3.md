# CLAUDE.md — v0.2.3 项目迭代指导文件

> 目标：把当前 `boundary` v0.2.2 升级为 v0.2.3。  
> v0.2.3 的核心是：**message DPO + teacher-as-utility-judge + vLLM candidate logprob mining + OR-Bench refusal 数据接入**。

---

## 0. v0.2.3 总目标

当前 v0.2.2 已完成：学生模型输出 top-k student-proposed candidates；不再用代码枚举所有动作并构造 gold-backed counterfactual；训练阶段使用 `U_rel`，eval 阶段使用 `U_real`；teacher prompt 已开始采用 rubric；pair 数据中已保存 `prompt_messages/chosen_messages/rejected_messages`。

但 v0.2.2 仍有关键断点：

1. DPO 训练实际仍可能消费 flat text 字段，而不是 message 数据；
2. 工具动作局部效用仍有自动 proxy，`CALCULATE/CLARIFY` 等动作评分较脆弱；
3. 当前 `LOW_LOGIT_MARGIN` 并非严格 logit / likelihood 信号；
4. eval / calibration / finalize 仍有旧逻辑残留；
5. refusal 数据覆盖不足。

v0.2.3 的升级目标：

```text
student top-k candidates
→ vLLM candidate action-part logprob scoring
→ teacher-as-utility-judge scores every candidate
→ message DPO pairs from student candidates only
→ OR-Bench added as fifth main dataset
→ eval/calibration use real executed branches
```

## 1. 第一轮审查中指出的 12 个必须处理的问题

以下 12 个问题来自对 v0.2.2 的第一轮完整静态审查。v0.2.3 必须逐项处理或明确留下 TODO。

### 问题 1：`parse_candidate_output()` 可能返回不含 `ANSWER` 的候选集

当前逻辑可能先检查到 `ANSWER` 存在于原始候选中，但之后截断 top-k 时把 `ANSWER` 截掉。  
这违反“`ANSWER` 必须作为统一候选动作之一出现”的核心约束。

**修复要求：**

- `ANSWER` 必须出现在最终返回的 top-k candidates 中；
- 如果原始输出没有 `ANSWER`，该样本直接 invalid，不做 repair reprompt；
- 如果原始输出有 `ANSWER`，但排序在 top-k 之外，应替换末位 candidate，确保最终 top-k 中包含 `ANSWER`；
- 不要硬编码 `3`，应读取 `rollout.top_k_actions`。

推荐逻辑：

```python
def enforce_answer_in_topk(candidates, top_k: int):
    actions = [c["action"] for c in candidates]
    if "ANSWER" not in actions:
        raise InvalidCandidateOutput("invalid_missing_answer")

    ordered = sorted(candidates, key=lambda c: int(c.get("rank", 999)))
    top = ordered[:top_k]

    if "ANSWER" not in [c["action"] for c in top]:
        answer_candidate = next(c for c in ordered if c["action"] == "ANSWER")
        if len(top) < top_k:
            top.append(answer_candidate)
        else:
            top[-1] = answer_candidate

    for i, c in enumerate(top, start=1):
        c["rank"] = i
    return top
```

### 问题 2：student candidates 没有按 `example.allowed_actions()` 过滤

学生可能在 GSM8K/MATH 中输出 `SEARCH`，或者在不允许 clarify 的任务里输出 `CLARIFY`。当前这类候选可能仍进入 teacher label / pair construction。

**修复要求：**

- 在 rollout candidate normalization 后，按 `example.allowed_actions()` 过滤；
- 被过滤的候选写入 diagnostics；
- 过滤后若少于 2 个有效候选，或缺少 `ANSWER`，该样本 invalid；
- 不允许 fallback branch 进入 training pair。

推荐逻辑：

```python
allowed = set(example.allowed_actions())
filtered = []
diagnostics = []
for cand in candidates:
    if cand["action"] not in allowed:
        diagnostics.append({
            "issue": "candidate_action_not_allowed",
            "action": cand["action"],
        })
        continue
    filtered.append(cand)
```

### 问题 3：eval 侧 finalize pass 当前是伪实现

当前 HF/vLLM policy 的 `finalize_after_tool()` 可能只是把 observation JSON 当成 final answer。  
这不是理论中的 “tool observation → student finalize answer”。

**修复要求：**

- `SEARCH / CALCULATE / CLARIFY` 在 eval/calibration 中必须执行真实 finalize pass；
- finalize prompt 必须实际喂给 student policy；
- final answer 应来自 student 生成，而不是 observation JSON；
- 如果 finalize 解析失败，写 diagnostics，并标记该 branch invalid for eval scoring。

需要新增或修正：

```python
policy.finalize_after_tool(
    prompt_messages=...,
    candidate=...,
    observation=...,
)
```

并确保 HF/vLLM 两种后端都真实生成。

### 问题 4：eval metrics 仍使用旧字段，当前主指标不可信

旧逻辑依赖：

- `natural_branch["utility"]`
- `natural_branch["outcome_label"]`
- `best_action`
- `natural_action == best_action`

但 v0.2+ 的 `best_action` 不应是学生 rank1，而应是 `argmax U_real`。

**修复要求：**

- eval 后新增 scoring pass；
- 每个 executed branch 计算 `utility_real`；
- 每条 record 写入：
  - `best_action_real`
  - `natural_action`
  - `natural_branch_real`
  - `branches[*].utility_real`
  - `branches[*].outcome_label_real`
- eval metrics 全部基于 `U_real` 和 `best_action_real`。

推荐逻辑：

```python
for record in eval_rollouts:
    branch_map = {b["action"]: b for b in record["branches"]}
    for branch in record["branches"]:
        branch["utility_real"] = utility_real(
            branch, example, branch_map, record["semantic_tags"], config
        )
    best = max(record["branches"], key=lambda b: b["utility_real"])
    record["best_action_real"] = best["action"]
```

### 问题 5：calibration 脚本不能直接在 train-side annotation rollout 上计算 `U_real`

训练 rollout 通常不执行工具、没有 observation/final answer/correctness。因此不能拿它直接算真实效用。

**修复要求：**

- calibration 必须读取或触发 eval-style executed rollout；
- calibration 比较的是：
  - `U_rel`：teacher judged / training estimator；

- 禁止在无 execution 的 annotation rollout 上计算 `U_real`；
- 若输入 record 没有真实 execution 字段，脚本应报错，而不是静默产出结果。

## 2. v0.2.3 必须改成 Message DPO

### 2.1 flat DPO 与 message DPO 的区别

flat DPO 是：

```json
{
  "prompt": "plain text prompt",
  "chosen": "plain text chosen completion",
  "rejected": "plain text rejected completion"
}
```

message DPO 是：

```json
{
  "prompt": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "Reasoning: ..."}
  ],
  "chosen": [
    {"role": "assistant", "content": "Meta-Reflection: ..."},
    {"role": "assistant", "content": "{\"action\":\"SEARCH\", ...}"}
  ],
  "rejected": [
    {"role": "assistant", "content": "Meta-Reflection: ..."},
    {"role": "assistant", "content": "{\"action\":\"ANSWER\", ...}"}
  ]
}
```

本项目的理论目标是学习：

\[
\pi_\theta(a_t \mid s_t)
\]

其中 action 是在 conversation state 后的下一步动作发射。因此 message DPO 更符合方法逻辑。

### 2.2 训练 pair 截止于 action emission

训练阶段 pair 只包含：

- prompt_messages：到当前状态 \(s_t\) 为止；
- chosen_messages：Meta-Reflection + Action JSON；
- rejected_messages：Meta-Reflection + alternative Action JSON。

训练 pair **不包含**：

- tool observation；
- post-tool finalize answer；
- 真实 tool execution 结果。

这些只用于 eval / calibration。

### 2.3 代码修改要求

在 `run_step_dpo.py` 中，进入 `DPOTrainer` 之前必须做格式转换：

```python
def to_message_dpo_row(pair: dict) -> dict:
    return {
        "prompt": pair["prompt_messages"],
        "chosen": pair["chosen_messages"],
        "rejected": pair["rejected_messages"],
    }

train_data = [to_message_dpo_row(p) for p in train_pairs]
eval_data = [to_message_dpo_row(p) for p in eval_pairs]
```

不要把 flat 字段传入 trainer。

如果当前 TRL 版本不能直接消费 conversational preference format，则做 deterministic chat-template flattening，但 canonical pair data 必须仍然保存 message fields。

### 2.4 保留 flat 字段的限制

可以继续在 pair JSONL 中保存：

- `prompt`
- `chosen`
- `rejected`

但只能用于 debug/export。训练入口必须明确使用 message DPO 路径。

## 3. Teacher-as-Utility-Judge：所有动作局部效用默认由 teacher 标注

### 3.1 改动目标

v0.2.3 中，`U_rel(a_t | s_t)` 的默认路径改为 teacher 标注。  
这意味着：

- `ANSWER`
- `SEARCH`
- `CALCULATE`
- `CLARIFY`
- `REFUSE`

所有候选动作都由 teacher 在给定题目、gold/reference、学生 reasoning、候选动作、语义 tag、过程特征的条件下打 utility/helpfulness 分。

自动规则不再作为主效用来源，只作为：

- teacher prompt evidence；
- diagnostics；
- fallback smoke test；
- ablation。

### 3.2 为什么这样改

原因：

1. `CALCULATE` proxy 对 MATH/GSM8K 过粗；
2. `CLARIFY` proxy 对 slot 语义匹配过粗；
3. `SEARCH` 不执行工具时很难靠规则判断 query 是否足够好；
4. `REFUSE` 判断依赖 false premise / unanswerable / over-refusal 边界；
5. gold/reference 只作为离线 judge 输入，不会污染 student 生成。

### 3.3 Teacher 输入必须包含

teacher utility judging 的输入至少包括：

```text
Question
Gold/reference answer or label
Dataset and task metadata
Student reasoning attempt
Student uncertainty summary
Student ranked candidates
Candidate action_input
Semantic tags and tag evidence
Process features
Candidate logprob scores, if available
```

特别注意：

- teacher 可以看到 gold/reference；
- teacher 不能用 gold 生成 action_input；
- teacher 不能模拟 tool observation；
- teacher 只能判断“该候选动作在当前状态下是否有用”。

### 3.4 Teacher 输出格式

替换或扩展 teacher 输出为：

```json
{
  "semantic_tags": [],
  "meta_reflection": "",
  "candidate_utility": [
    {
      "rank": 1,
      "action": "ANSWER",
      "score": 0.0,
      "reason": "",
      "failure_mode": "correct_answer|wrong_answer|unnecessary_tool|useful_tool|justified_refuse|over_refuse|bad_query|bad_expression|bad_clarify_question"
    }
  ],
  "recommended_action": "",
  "rationale": "",
  "preferred_over": [],
  "rubric_degenerate": false
}
```

`candidate_helpfulness` 可以保留向后兼容，但主字段应改为 `candidate_utility`。

### 3.5 Utility 公式

推荐：

\[
U_{rel}(a_t | s_t)
=
teacher\_utility(a_t | s_t, gold)
-
cost(a_t)
+
semantic\_bonus(a_t, z_{sem})
\]

其中：

```text
cost(ANSWER) = 0
cost(SEARCH) = lambda_tool
cost(CALCULATE) = lambda_calc
cost(CLARIFY) = lambda_clar
cost(REFUSE) = lambda_refuse or 0
```

semantic bonus 只保留小幅 action-compatible bonus：

```text
+0.1 if TIME_SENSITIVE or NEW_OR_TAIL_KNOWLEDGE and action=SEARCH
+0.1 if CALCULATION_REQUIRED and action=CALCULATE
+0.1 if MISSING_INFO or CLARIFY_REQUIRED and action=CLARIFY
+0.1 if FALSE_PREMISE or JUSTIFIED_REFUSE and action=REFUSE
```

process features 不进入 utility。

### 3.6 Teacher prompt 修改方向

teacher system prompt 应强调：

```text
Gold/reference is provided only for judging candidate utility.
Do NOT use gold/reference to invent a tool observation.
Do NOT assume SEARCH will retrieve the gold answer unless the candidate query is specific and relevant.
Do NOT reward CALCULATE unless the expression is concrete and relevant.
Do NOT reward CLARIFY unless the question targets a critical missing slot.
Score the candidate action as emitted by the student.
```

## 4. vLLM Candidate Action-Part Logprob Scoring

### 4.1 改动目标

当前 `LOW_LOGIT_MARGIN` 不够严格。  
v0.2.3 用两阶段 vLLM 流程替代它：

1. 第一轮：生成 top-k candidates；
2. 第二轮：对每个 candidate 分别计算 action 部分的 logprob mean。

该分数用于：

- process features；
- boundary mining；
- teacher prompt evidence；
- calibration 分析。

不得直接作为 `U_rel` 主体。

### 4.2 评分对象

对每个 candidate 构造 action emission completion：

```json
{"action": "SEARCH", "action_input": {"query": "..."}}
```

如果当前 completion messages 是：

```json
[
  {"role": "assistant", "content": "Meta-Reflection: ..."},
  {"role": "assistant", "content": "{\"action\":\"SEARCH\", ...}"}
]
```

则 action-part logprob 只计算第二条 assistant message 中 action JSON 部分，而不包含 meta-reflection。

### 4.3 计算方式

设 prompt 为 \(P\)，candidate action JSON 为 \(A_i\)。用 teacher-forced scoring 计算：

\[
S_i =
\frac{1}{|A_i|}
\sum_{j=1}^{|A_i|}
\log p_\theta(A_{ij} \mid P, A_{i,<j})
\]

保存为：

```json
{
  "rank": 1,
  "action": "SEARCH",
  "action_json_logprob_sum": -18.7,
  "action_json_logprob_mean": -0.83,
  "action_json_num_tokens": 22,
  "missing_logprob_positions": 0
}
```

### 4.4 vLLM 实现建议

新增方法：

```python
class VLLMLocalPolicy:
    def score_candidate_action_logprobs(
        self,
        prompt_messages: list[dict],
        candidates: list[dict],
        tokenizer,
    ) -> list[dict]:
        ...
```

推荐 config：

```yaml
rollout:
  candidate_logprob_scoring:
    enabled: true
    prompt_logprobs: 1
    score_action_json_only: true
    normalize: mean
    use_prefix_caching: true
    fallback_full_vocab_on_missing: false
    entropy_temperature: 1.0
    low_margin_delta: 0.10
    high_entropy_threshold: 0.85
    confidence_high_threshold: 0.75
    logprob_low_percentile: 0.30
```

vLLM 初始化应启用 prefix caching：

```python
LLM(..., enable_prefix_caching=True)
```

### 4.5 token boundary

不要用字符串长度截断 action part。应使用 tokenizer ids。

推荐：

```python
prefix_ids = tokenizer.apply_chat_template(
    prompt_messages,
    tokenize=True,
    add_generation_prompt=True,
)

full_ids = tokenizer.apply_chat_template(
    prompt_messages + action_messages,
    tokenize=True,
    add_generation_prompt=False,
)

start = longest_common_prefix_len(prefix_ids, full_ids)
action_token_ids = full_ids[start:]
```

如果需要只打 action JSON 而不打 meta-reflection，则对 action JSON 单独构造 assistant content 或使用 marker 定位。

## 5. 新 process tags：替代原 `LOW_LOGIT_MARGIN`

v0.2.3 删除或废弃原 `LOW_LOGIT_MARGIN` 主标签。新增以下 process tags，这里在 teacher 的 prompt 中也要添加关于新标签的说明。

### 5.1 `LOW_CANDIDATE_LOGPROB_MARGIN`

定义：

```text
top1_mean_logprob - top2_mean_logprob < δ
```

其中 mean_logprob 越高代表模型越偏好该 candidate。top1/top2 按 `action_json_logprob_mean` 排序。

实现：

```python
scores = sorted(candidate_scores, key=lambda x: x["action_json_logprob_mean"], reverse=True)
margin = scores[0]["action_json_logprob_mean"] - scores[1]["action_json_logprob_mean"]
LOW_CANDIDATE_LOGPROB_MARGIN = margin < cfg.low_margin_delta
```

### 5.2 `RANK_DISAGREEMENT`

定义：

```text
self_reported_rank != logprob_rank
```

更具体：学生自报 rank1 action 与 logprob rank1 action 不同。

实现：

```python
student_rank1 = candidates[0]["action"]
logprob_rank1 = max(candidate_scores, key=lambda x: x["action_json_logprob_mean"])["action"]
RANK_DISAGREEMENT = student_rank1 != logprob_rank1
```

可选扩展：使用 Spearman/Kendall rank correlation。

### 5.3 `HIGH_SCORE_ENTROPY`

定义：

```text
softmax(candidate_mean_logprobs / τ) entropy high
```

实现：

```python
probs = softmax([s["action_json_logprob_mean"] / tau for s in candidate_scores])
entropy = -sum(p * log(p) for p in probs)
normalized_entropy = entropy / log(len(probs))
HIGH_SCORE_ENTROPY = normalized_entropy >= cfg.high_entropy_threshold
```

### 5.4 `CONFIDENCE_LOGPROB_MISMATCH`

定义：

```text
self-reported confidence high, but sequence logprob low
```

推荐实现：

```python
CONFIDENCE_LOGPROB_MISMATCH = (
    candidate["confidence"] >= cfg.confidence_high_threshold
    and candidate_score["action_json_logprob_mean"] <= running_low_logprob_threshold
)
```

其中 `running_low_logprob_threshold` 可以是当前 batch / 数据集 / calibration set 的 30% 分位数。

### 5.5 旧标签处理

- `LOW_LOGIT_MARGIN` 标记为 deprecated；
- 不再用于 boundary mining 主逻辑；
- 若保留，只作为 backward-compatible alias，不进入论文指标。

## 6. Boundary Mining 更新

v0.2.3 的 boundary score 应使用：

- utility margin；
- candidate action diversity；
- 新 process tags；
- semantic boundary pressure。

推荐：

\[
B(s_t)
=
\alpha \cdot \text{small U_rel margin}
+
\beta \cdot \text{action diversity}
+
\gamma \cdot \text{candidate logprob uncertainty}
+
\delta \cdot \text{semantic pressure}
\]

其中 candidate logprob uncertainty 包括：

- `LOW_CANDIDATE_LOGPROB_MARGIN`
- `RANK_DISAGREEMENT`
- `HIGH_SCORE_ENTROPY`
- `CONFIDENCE_LOGPROB_MISMATCH`

示例权重：

```yaml
mining:
  boundary_score_weights:
    low_u_rel_margin: 0.25
    action_diversity: 0.15
    low_candidate_logprob_margin: 0.15
    rank_disagreement: 0.10
    high_score_entropy: 0.10
    confidence_logprob_mismatch: 0.10
    semantic_pressure: 0.15
```

## 7. OR-Bench：作为主第五数据集加入

### 7.1 当前主数据集

v0.2.3 后，主训练数据集建议为五类：

1. `gsm8k`：基础数学推理；
2. `math`：更强数学推理；
3. `in3`：意图缺失 / clarify；
4. `mintqa`：新知识 / 长尾知识 / search；
5. `or_bench`：refusal / over-refusal boundary。

FreshQA / TruthfulQA / RealTimeQA 可作为 eval/OOD 扩展，不计入主五训练集。

### 7.2 OR-Bench 的作用

OR-Bench 用于训练和评估：

- benign but suspicious prompts：应该 `ANSWER`，不应过拒答；
- toxic / actually unsafe prompts：应该 `REFUSE`；
- hard prompts：形成 `ANSWER` vs `REFUSE` 的边界样本。

这与 action calibration 主线一致。

### 7.3 Adapter 要求

新增：

```text
src/mcagent_boundary/adapters/or_bench.py
```

注册到：

```text
src/mcagent_boundary/adapters/__init__.py
```

Adapter 输出 `StandardizedExample`，metadata 至少包含：

```json
{
  "boundary_type": "refusal",
  "task_type": "refusal_boundary",
  "can_search": false,
  "can_calculate": false,
  "can_clarify": false,
  "allow_refuse": true,
  "or_bench_label": "benign|toxic|hard",
  "should_refuse": true
}
```

### 7.4 动作空间

OR-Bench 默认允许：

```text
ANSWER
REFUSE
```

可选允许 `SEARCH` 作为 ablation，但主实验中不建议开启，以免把 refusal boundary 混成 factual verification。

### 7.5 Utility 判断

teacher 看到：

- prompt；
- OR-Bench label；
- gold/refusal label；
- student candidates；
- student reasoning。

teacher 判断：

- 若 `should_refuse=true`：
  - `REFUSE` 高 utility；
  - `ANSWER` 低 utility，尤其 unsafe compliance；
- 若 `should_refuse=false`：
  - `ANSWER` 高 utility；
  - `REFUSE` 低 utility，标记 over-refusal。

### 7.6 Metrics

新增 per-dataset refusal metrics：

```text
over_refusal_rate:
  benign examples where natural_action=REFUSE

under_refusal_rate:
  toxic examples where natural_action=ANSWER

refusal_action_accuracy:
  natural_action matches should_refuse label

answer_vs_refuse_calibration:
  U_rel / model confidence separates ANSWER-needed vs REFUSE-needed states
```

## 10. 推荐实施顺序

### Phase 1 — parser / candidate validity hardening

- 修 `ANSWER` 保留 bug；
- 传入 config top_k；
- 过滤 disallowed actions；

### Phase 2 — message DPO

- 修改 `run_step_dpo.py`；
- trainer dataset 只传 message DPO 格式；

- teacher prompt 增加 gold/reference；
- teacher 输出 `candidate_utility`；
- `utility_rel()` 默认读取 teacher score；

### Phase 4 — vLLM candidate logprob scoring

- 实现 candidate action JSON logprob mean；
- 新 process tags；

### Phase 5 — eval/calibration hardening

- eval branch 真执行；
- tool finalize 真调用 student；
- 计算 `U_real`；
- calibration 用 executed rollout。

### Phase 6 — OR-Bench adapter

- 新增 adapter；
- 加入主训练 datasets；
- 增加 refusal metrics。

## 11. v0.2.3 验收标准

只有满足以下条件，才算 v0.2.3 完成：

1. 最终 top-k candidates 一定包含 `ANSWER`；
2. candidates 全部属于 `example.allowed_actions()`；
3. invalid schema / missing ANSWER / single-action response 只写 diagnostics，不进入训练；
4. DPOTrainer 实际消费 message DPO 数据；
5. flat DPO 字段不作为 trainer 输入；
6. teacher 默认给所有 candidate 打 `candidate_utility`；
7. `U_rel` 默认由 teacher utility 构成，而不是 calculate/clarify proxy；
8. gold/reference 只进入 teacher utility judging，不进入 student prompt/action/tool observation；
9. vLLM 二阶段 scoring 输出 action JSON logprob mean；
10. `LOW_LOGIT_MARGIN` 被新 process tags 替代；
11. boundary mining 使用新 process tags；
12. eval rollout 执行真实 tool + finalize；
13. calibration 对比的是 `U_rel` vs executed `U_real`；
14. OR-Bench 作为第五主数据集接入；
15. 主实验禁用 heuristic fallback。

## 12. 最终原则

v0.2.3 的核心原则是：

```text
候选动作必须来自学生；
动作效用必须由 teacher/gold 离线判断；
模型不确定性必须来自候选动作似然和排序冲突；
训练必须在 message-level action emission 上完成；
真实工具执行只用于 eval/calibration。
```

这会把项目从“可运行原型”推进到“论文实验可用版本”。
